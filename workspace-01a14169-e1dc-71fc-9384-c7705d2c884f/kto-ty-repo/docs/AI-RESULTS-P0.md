# P0: результаты AI не отвечают теме теста

## Сообщение владельца

> «ии выдает как результат теста полную хрень не связанную с вопросом»

Статус: **открыто, не исправлено**. Конкретный проблемный тест, ответы и текст результата еще не предоставлены. Не выдумывать их.

## Что видно из исходников

### Worker

`ai(env, title, history)` в `worker.js` выбирает финальную генерацию при `history.length >= 5`. Запрос к Groq содержит `topic: title`, все ответы и `response_schema`. Параметры: модель `openai/gpt-oss-120b`, temperature `0.9`, JSON mode, max_completion_tokens `3500`.

В `/api/answer` тема берется через JOIN sessions → quizzes; текущий вопрос и ответ добавляются в историю до вызова AI. Перед финальным запросом должно быть ровно пять пар question/answer. Эта механика покрыта офлайн контрактным тестом, но не доказана для конкретной сессии владельца.

Результат проверяется в основном структурно: title — строка, paragraphs — массив строк. **Нет проверки, что сущность результата относится к теме, что ответы реально обосновывают вывод, что выбран существующий персонаж нужной вселенной, что числовой вопрос получил число.** Отсутствие такой проверки установлено из кода; это не доказывает единственную причину пользовательского бага.

Вопросы и ответы генерируются последовательно без предварительного плана, явного типа результата, списка допустимых исходов и устойчивой шкалы. Системная инструкция для финала все еще содержит указания задавать вопросы. Это гипотезы риска, не подтвержденный диагноз.

### Python

`next_step(title, history)` в `server.py` реализует похожую, но не идентичную логику. Деплой на Cloudflare использует Worker, не Python. Проверять обе версии или явно документировать временное расхождение.

### Картинки

Поиск Wikipedia использует английский image_query от модели. Резервные фото ограничены cat/forest/space/flowers/sea. Даже правильный текст может получить только приблизительную картинку — это отдельная проблема, не замена исправлению результата.

## План следующей сессии

1. Уточнить у владельца: тема, пять ответов, плохой результат/ссылка, URL сайта, какая версия задеплоена. Не запрашивать ключ в чате. Можно начать на синтетических данных, не блокируя всю работу вопросами.
2. Проследить путь `quiz.title → session.quiz_id → history.current → answers → prompt → JSON → saved result → renderResult` в `static/app.js`. Исключить перепутанные сессии/старый сохраненный результат/старый deployment.
3. На живом Groq воспроизвести несколько тем: гном; количество котов; Genshin; хлеб; планета. Проверять повторяемость, не единственный удачный прогон.
4. Рассмотреть разделение prompt для вопросов и результата. Ввести контракт типа результата: fandom_character / numeric / object_type и явный ответ на исходную тему. Возможен план с допустимыми исходами и критериями; решение выбирать после воспроизведения.
5. Для фандомов продумать достоверный набор персонажей и проверку принадлежности. Не придумывать канон и не принимать любой текст только потому, что он валидный JSON.
6. Добавить строгую структурную и тематическую валидацию. Если валидация провалена — ограниченная регенерация с указанием причины, затем честная ошибка, а не сохранение нерелевантного результата. Учитывать расходы/лимиты Groq. Самопроверка той же моделью не является достаточной независимой гарантией.
7. Снизить случайность финального вывода как эксперимент, не объявлять снижение temperature полным исправлением.
8. Сохранять воспроизводимые обезличенные кейсы/оценки, обновить `npm test` и TODO. Если меняется схема D1 — только новая миграция с обратной совместимостью старых результатов.

## Критерии приемки

- «Кто ты из Genshin Impact?» → назван реальный персонаж Genshin, а не гном/абстрактный тип.
- «Сколько в тебе котов?» → явное количество, не только описание характера.
- «Какой ты хлебушек?» → конкретный вид хлеба/выпечки.
- «Какая ты планета?» → название планеты.
- Результат обоснован как минимум несколькими реально данными ответами; не цитирует несуществующие ответы.
- Противоположные наборы ответов дают объяснимо разные выводы; одинаковые ответы не должны каждый раз вести в произвольную вселенную.
- В финале нет нового вопроса и вариантов ответа; формат совместим с фронтендом.
- Ошибочный результат не записывается как успешно завершенный и не увеличивает plays.
- JSON-парсинг, ретраи и поиск картинок не скрывают провал качества.

Синтетические темы находятся в `tests/fixtures/quality-cases.json`. Сами по себе они не являются автоматическим semantic evaluator.
